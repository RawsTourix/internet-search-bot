# План реализации и завершения v0.4

## Именованные updates

### `v0.4-storage-foundation`

- `ContentStore`;
- `ArtifactStore`;
- models refs;
- filesystem backend;
- atomic writes;
- configuration.

### `v0.4-result-compaction`

- `result_handling`;
- relative budgets;
- raw result persistence;
- single-pass LLM-summary;
- oversized fallback;
- progress/trace events.

### `v0.4-cycle-compaction`

- active cycle object;
- atomic segment selection;
- `CycleWorkingMemory`;
- no summary tree;
- generations;
- recovery tests.

### `v0.4-dag-planning`

- filesystem `PlanStore` with revisions and optimistic concurrency;
- typed `AgentPlan` / `PlanNode` models;
- computed ready/stalled projections;
- `PlanningService` validation and strict node transitions;
- command-oriented manager tools;
- bounded `ActivePlanState` in runtime context;
- runtime-owned plan/node/result/artifact refs;
- tool-call association и final-answer guard;
- progress/trace events without scheduler semantics.

### `v0.4-file-artifacts`

- durable `ClientIngressEvent` и initial `InputBatchDraft`;
- streaming `ContentStore` ingress/egress;
- artifact lineage и immutable versions;
- format registry и bounded text operations;
- artifact manager tools и MCP bindings;
- candidate promotion и provenance;
- `AgentResult.artifacts`;
- durable response outbox и Telegram/Web delivery.

### `v0.4-file-artifacts-advanced`

- server-owned capability registry и immutable snapshots;
- semantic `InputPart`/`OutputPart`;
- localization;
- deterministic response anchor и presentation lifecycle;
- commit-once `OutputBatch`;
- native client delivery plan;
- receipts, recovery и READY outbox;
- exact client authority и artifact-content evidence.

### `v0.4-input-runtime`

- immutable `CommittedInputBatch`;
- `CycleInbox<CommittedInputBatch>` with leases/idempotency;
- session admission и runtime manifest;
- safe checkpoints и batch update messages;
- `SessionControlInbox`;
- per-session lock и finalization race guard;
- resume/replay after restart.

### `v0.4-runtime-modularization`

- characterization baseline;
- models/config extraction;
- `LLMClient` port;
- самостоятельный MCP runtime;
- tool registry/dispatcher;
- context management;
- event/trace contracts;
- finalization pipeline;
- session/cycle/run repositories;
- composition-based runtime extensions;
- `AgentRuntime` и application composition root;
- compatibility cleanup.

Подробности: [`v0.4-runtime-modularization/README.md`](v0.4-runtime-modularization/README.md).

## Порядок реализации

```text
1. v0.4-storage-foundation
2. v0.4-result-compaction
3. v0.4-cycle-compaction
4. v0.4-dag-planning
5. v0.4-file-artifacts
6. v0.4-file-artifacts-advanced
7. v0.4-input-runtime
8. v0.4-runtime-modularization
9. full integration and architecture tests
10. documentation/current baseline stabilization
```

Storage идёт первым, потому что все последующие подсистемы используют refs.
Input runtime идёт после artifacts, потому что `InputBatch` может содержать
attachments. Modularization идёт после functional v0.4, чтобы refactor опирался
на завершённые contracts и characterization tests.

## Acceptance criteria v0.4

### Small/large/oversized result и cycle compaction

```text
small result → inline → immediate use
large result → original persisted → compact/store_only → no raw in context
oversized result → needs_retrieval=true → no false complete summary
context trigger → closed atomic segment → one CycleWorkingMemory
repeated compaction → one visible generation → no summary tree
```

### DAG

```text
invalid mutation/revision
→ validation/conflict
→ stored plan remains intact
```

```text
active plan + no in_progress node
→ substantive tool call blocked
```

```text
active unresolved plan + final answer
→ reconciliation or controlled resumable handoff
```

### Atomic client input

```text
Web multipart text + files
→ all streams stored and validated
→ one committed InputBatch
→ one cycle
```

```text
one attachment fails
→ batch failed
→ cycle not started with partial input
```

### Telegram grouping

```text
media_group messages
→ one draft by media_group_id
→ quiet + sealing
→ one committed InputBatch
```

```text
late media-group fragment after commit
→ continuation batch
→ original batch remains immutable
```

### Artifact versioning and interaction

```text
agent edits text artifact
→ new art_* version in same lineage
→ original exact version remains available
→ stale current_artifact_id rejected
```

```text
binary processor returns modified bytes
→ content candidate
→ explicit new version
→ no arbitrary local path in LLM context
```

```text
cycle compaction
→ authoritative artifact catalog/read/delivery state rebuilt from stores
→ LLM summary is not source of truth
```

### Active-cycle input

```text
batch during LLM/tool execution
→ durable CycleInbox
→ current atomic action finishes
→ batch applied at safe checkpoint
```

```text
batch accepted before terminal commit
→ stale DONE/WAITING_USER suppressed
→ cycle continues
```

```text
duplicate input/inbox replay
→ applied once by stable IDs
```

### Delivery

```text
final answer + deliverable artifact
→ durable output/outbox
→ client-specific streaming/native delivery
→ independent text/file receipts
```

```text
process restart after final LLM answer
→ outbox replay/reconciliation
→ no repeated agent cycle
```

### Recovery and scope

```text
restart
→ persisted drafts/batches/inbox/outbox and resumable cycle recovered
```

```text
group chat users
→ session/grouping policy prevents accidental cross-user file access
```

### Runtime modularization

```text
same scenario before/after refactor
→ equivalent AgentResult/status/can_resume
→ protocol-valid equivalent LLM/tool sequence
→ equivalent refs, plan/artifact state and delivery intent
```

Дополнительно:

- `AgentRuntime` не зависит от FastAPI, Telegram или concrete persistence;
- MCP runtime самостоятельно владеет connections/registry/recovery;
- LLM provider вызывается через port;
- planning/artifacts подключаются композиционно;
- import модуля не запускает global application lifecycle;
- filesystem/local mode проходит полный regression suite;
- v0.5 может добавить PostgreSQL adapters без изменения agent loop;
- v0.6 может создать runtime в worker entrypoint.

## Что переносится в v0.5

- PostgreSQL implementations для stores/repositories;
- transactional session admission и terminal commit;
- persistent artifact lineage/version/delivery relations;
- lazy extraction сложных файлов;
- page/sheet/slide/section representations;
- persistent chunk cache и embeddings;
- keyword/semantic/hybrid RAG;
- search over old cycles/results/artifacts;
- provenance-aware retrieval;
- processing oversized sources by parts;
- durable resume after process restart;
- optional object storage payload backend.

## Что переносится в v0.6

- Redis/arq и distributed leases;
- durable distributed jobs/AgentRun/TaskRun;
- workflow scheduler и parallel nodes;
- background extraction, conversion, scanning и delivery;
- progress event bus и Notification/Delivery boundary;
- background summarization и cleanup workers;
- remote/resumable large uploads;
- object storage как multi-process transport;
- service/process boundaries.

Полноценный execution sandbox не относится к v0.6: contracts могут быть
подготовлены заранее, single-node isolated execution начинается в v0.9, а
runner fleet — в v0.10.
