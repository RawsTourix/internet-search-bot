## Порядок реализации

```text
1. v0.4-storage-foundation
2. v0.4-result-compaction
3. v0.4-cycle-compaction
4. v0.4-dag-planning
5. v0.4-file-artifacts
6. v0.4-file-artifacts-advanced
7. v0.4-batch-workflows
8. v0.4-input-runtime
9. v0.4-runtime-modularization
10. v0.4-mcp-registry-foundation
11. full integration and architecture tests
12. documentation/current baseline stabilization
```

Storage идёт первым, потому что все последующие подсистемы используют refs.
Batch workflows завершают transport/assembly/client presentation до active-cycle
additions. Input runtime идёт после них, потому что принимает только уже
committed batches и опирается на artifact/output lifecycle. Modularization идёт
после functional v0.4, чтобы refactor опирался на завершённые contracts и
characterization tests. MCP registry foundation идёт после modularization,
потому что использует выделенные `AgentRuntime`, `ToolDispatcher`, MCP runtime,
ConfigProvider и lifecycle hook ports.

## Acceptance criteria v0.4

### Small/large/oversized result и cycle compaction

```text
small result → inline → immediate use
large result → original persisted → compact/store_only → no raw in context
oversized result → needs_retrieval=true → no false complete summary
context trigger → closed atomic segment → one CycleWorkingMemory
repeated compaction → one visible generation → no summary tree
```

### DAG

```text
invalid mutation/revision
→ validation/conflict
→ stored plan remains intact
```

```text
active plan + no in_progress node
→ substantive tool call blocked
```

```text
active unresolved plan + final answer
→ reconciliation or controlled resumable handoff
```

### Atomic client input

```text
Web multipart text + files
→ all streams stored and validated
→ one committed InputBatch
→ one cycle
```

```text
one attachment fails
→ batch failed
→ cycle not started with partial input
```

### Telegram grouping и batch workflows

```text
media_group messages
→ one draft by media_group_id
→ quiet + sealing
→ one committed InputBatch
```

```text
late media-group fragment after commit
→ continuation batch
→ original batch remains immutable
```

```text
explicit collection
→ /collect + text/files + /send
→ one committed InputBatch
→ one run presentation/final output
```

### Artifact versioning and interaction

```text
agent edits text artifact
→ new art_* version in same lineage
→ original exact version remains available
→ stale current_artifact_id rejected
```

```text
binary processor returns modified bytes
→ content candidate
→ explicit new version
→ no arbitrary local path in LLM context
```

```text
cycle compaction
→ authoritative artifact catalog/read/delivery state rebuilt from stores
→ LLM summary is not source of truth
```

### Active-cycle input

```text
batch during LLM/tool execution
→ durable admission/CycleInbox
→ current atomic action finishes
→ batch applied at safe checkpoint
→ same cycle continues
```

```text
multiple additions
→ strict cycle sequence
→ boundaries preserved
→ applied exactly once
```

```text
batch accepted before terminal commit
→ stale DONE/WAITING_USER suppressed
→ cycle continues
```

```text
/stop
→ current atomic block completes
→ messages/plan/results/artifacts preserved
→ paused_by_user
```

```text
paused + additions + /continue
→ additions applied in order
→ same cycle resumes
```

```text
send_user_message
→ durable intermediate emission
→ client delivery independent
→ cycle remains running
```

```text
restart
→ admission/inbox/control/snapshot/finalization reconciled
→ no duplicate update/cycle/side effect
```

Полный contract:
[`v0.4-input-runtime/contracts-and-acceptance.md`](v0.4-input-runtime/contracts-and-acceptance.md).

### Delivery

```text
final answer + deliverable artifact
→ durable output/outbox
→ client-specific streaming/native delivery
→ independent text/file receipts
```

```text
process restart after final LLM answer
→ outbox replay/reconciliation
→ no repeated agent cycle
```

### Recovery and scope

```text
restart
→ persisted drafts/batches/inbox/outbox and resumable cycle recovered
```

```text
group chat users
→ session/grouping policy prevents accidental cross-user file access
```

### Runtime modularization

```text
same scenario before/after refactor
→ equivalent AgentResult/status/can_resume
→ protocol-valid equivalent LLM/tool sequence
→ equivalent refs, plan/artifact state and delivery intent
```

```text
valid agent.config change
→ new immutable revision
→ next operation uses it
→ no mandatory Gateway restart
```

```text
invalid agent.config change
→ previous valid snapshot remains active
```

```text
active AgentCycle + config reload
→ cycle keeps original revision
→ next cycle may use new revision
```

Дополнительно:

- `AgentRuntime` не зависит от FastAPI, Telegram или concrete persistence;
- MCP runtime самостоятельно владеет connections/recovery;
- LLM provider вызывается через port;
- configuration loading имеет одного owner — `ConfigProvider`;
- planning/artifacts подключаются композиционно;
- import модуля не запускает global application lifecycle;
- filesystem/local mode проходит полный regression suite;
- v0.5 может добавить PostgreSQL adapters без изменения agent loop;
- v0.6 может создать runtime в worker entrypoint.

### MCP registry foundation

```text
legacy mcp.config
→ equivalent server/tool availability after migration
```

```text
builtin/instance/user/session definitions
→ deterministic visible snapshot and revision
```

```text
new builtin definition
→ Streamable HTTP
```

```text
user definition
→ Streamable HTTP or stdio/executable
→ conservative trust unless separately approved
```

```text
trusted builtin tool
→ semantic localized progress

unknown tool
→ generic safe progress
```

```text
safe tool + recoverable transport failure
→ bounded retry by declared policy
```

```text
mutating tool + lost response
→ outcome unknown
→ no automatic repeated side effect
```

```text
remote handle created
→ exact server/resource/owner registration
→ independent from MCP transport connection
```

```text
cycle completed/failed/cancelled/reset/shutdown
→ bounded cleanup request
→ cleanup failure does not invalidate completed AgentResult
```

```text
optional builtin server unavailable/incompatible
→ controlled degraded capability
→ unrelated runtime remains operational
```

## Что переносится в v0.5

- PostgreSQL implementations для v0.4 repositories;
- transactional commit/admission/watermark/finalization boundaries;
- durable session/cycle/workspace recovery at database level;
- persistent artifact lineage/version/delivery relations;
- lazy extraction сложных файлов;
- page/sheet/slide/section representations;
- persistent chunk cache и embeddings;
- keyword/semantic/hybrid RAG;
- search over old cycles/results/artifacts;
- provenance-aware retrieval;
- processing oversized sources by parts;
- optional object storage payload backend.

## Что переносится в v0.6

- Redis/arq и distributed leases;
- durable distributed jobs/AgentRun/TaskRun;
- workflow scheduler и parallel nodes;
- `UserIntervention` routing поверх `CycleInbox`;
- context/task branch fork/join и controlled merge;
- background extraction, conversion, scanning и delivery;
- progress event bus и Notification/Delivery boundary;
- background summarization и cleanup workers;
- remote/resumable large uploads;
- object storage как multi-process transport;
- service/process boundaries;
- PostgreSQL-backed/distributed capability registry, worker-visible revisions и
  ownership-aware synchronization существующих v0.4 scopes.

Полноценный execution sandbox не относится к v0.6: contracts могут быть
подготовлены заранее, single-node isolated execution начинается в v0.9, а
runner fleet — в v0.10.
